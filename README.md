# The EPL Oracle

A Premier League fixture dashboard showing Jev through Vercel AI Gateway and OpenAI Decisions forecasts. Deploys to Vercel as a static frontend plus serverless functions, with Neon Postgres persistence after a verified migration.

## Architecture

- **Persistence is selected explicitly.** `PERSISTENCE_BACKEND=blob` retains the original three JSON files until cutover. `PERSISTENCE_BACKEND=neon` uses fixtures, runs, input snapshots, prediction revisions, attempts and results in Postgres. Neon imports must pass validation before the application can use them. API requests read persisted data; they do not call prediction providers.
- **Fixture and prediction schedules operate independently:**
  - `/api/cron/fixtures` runs daily, fetches the official fixture list and club stats from the Fantasy Premier League API, rebuilds the upcoming-fixture list, and saves actual results.
  - `/api/cron/predictions` starts the weekly run Wednesday at 09:00 Europe/London. UTC cron calls continue through Thursday 09:00 London so a missed start can recover the same run. Database claims prevent overlapping calls from duplicating a provider request.
- **Read-only API routes serve the frontend:** `/api/fixtures` merges the persisted fixture list with each provider’s latest successful forecast; `/api/results` returns Jev's resolved track record and a running accuracy total.
- There is no manual "predict this match" control — weekly forecasts are generated by the scheduled run, never on demand.

## Run locally

```sh
npm install
vercel link      # first time only, links this directory to a Vercel project
vercel env pull .env.local
vercel dev        # do not wrap this in an npm script — `vercel dev` detects and refuses that recursion
```

For dual predictions, configure `AI_GATEWAY_API_KEY`, `OPENAI_API_KEY`, `DATABASE_URL` and `PERSISTENCE_BACKEND=neon` in `.env.local`. Use a validated, isolated `DATABASE_SCHEMA` for local and preview work so manual jobs do not change production. Keep the Blob token for migration and rollback. Once the schema is initialized and imported, you can trigger jobs locally:

```sh
curl http://localhost:3000/api/cron/fixtures
curl http://localhost:3000/api/cron/predictions
```

Run `npm test` for fixture, prediction, accuracy and migration-source tests. Set `TEST_DATABASE_URL` to also run real PostgreSQL integration tests; these use a temporary schema and remove it afterward. See [migration and rollback](docs/neon-migration.md) for the database verification and cutover procedure.

## Deploy to Vercel

1. `vercel link` then `vercel` (or push to a Git repo connected to a Vercel project).
2. Add a **Blob** store to the project (Storage tab) — this sets `BLOB_READ_WRITE_TOKEN` automatically for all environments.
3. Set `AI_GATEWAY_API_KEY` and `OPENAI_API_KEY` as server-only credentials. For Neon, also set the pooled `DATABASE_URL` and complete [migration validation](docs/neon-migration.md) before setting `PERSISTENCE_BACKEND=neon`. Keep the Blob token for migration and rollback.
4. Optionally set `CRON_SECRET` — Vercel then sends it back as a Bearer token on every Cron Jobs request, and `/api/cron/*` verifies it before doing anything.
5. Deploy. `vercel.json` registers daily fixture refresh and separate once-daily UTC prediction entries for Wednesday's start and Thursday's recovery period. The London-time guard covers both GMT and BST; Vercel Hobby may invoke within the scheduled UTC hour. Before data is loaded, the fixtures endpoint reports "not loaded yet". Neon requires an initialized schema and verified import before serving data.

## Behaviour

- Shows all unstarted future fixtures, including undated ones, with pagination, team search and gameweek filtering.
- Every Wednesday, predictions cover dated, unstarted fixtures in the next 240 hours from the scheduled run time. Both providers refresh even when evidence is unchanged. A new run requires fixture data no older than 24 hours; recovery reuses the saved snapshot. Older successful forecasts remain visible with their generation date and an earlier-evidence label. Neon preserves earlier revisions and input snapshots, and saves each successful forecast with its attempt status.
- Sends both providers equivalent current-season league records, goals and the five most recent completed matches for each team. No fabricated fixtures, predictions or fallback model.
- Calls `POST https://ai-gateway.vercel.sh/v1/evaluate` with model `typesafe-ai/jev`. One choice question evaluates home/draw/away and one selects a score from 0–6 goals per team. Score and outcome are independent model decisions and can disagree.
- Once a fixture finishes, its prediction is compared against the real result and added to the **track record**: outcome-correct and exact-score-correct are tracked separately, alongside a running accuracy total across the whole season.
- Calls `POST https://api.openai.com/v1/decisions` with `gpt-6-luna`. The adapter converts the same outcome and score questions to named choice questions and rejects refused, incomplete or invalid responses. It retains the returned model identity.
- Both providers use an immutable shared fixture snapshot within a run. Each success commits separately. A failed provider cannot erase another provider’s forecast; missing forecasts are labelled explicitly. Detailed retry statuses are delivered in issue #4.
- Fixture cards show separate Jev and OpenAI Decisions opinions, probabilities, outcome, exact score, actual model and London generation timestamp. Outcome and score can disagree. Results and track-record scoring remain Jev-only until issues #5 and #6.

## Credentials

`AI_GATEWAY_API_KEY`, `OPENAI_API_KEY`, `BLOB_READ_WRITE_TOKEN` and `DATABASE_URL` are server-only Vercel environment variables, never sent to the browser. The app has no authentication of its own — before making this a public product, add one, plus per-user rate limits.
